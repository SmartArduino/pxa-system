# Core 2 与游戏命令借用探索（2026-10-11）

后续实现已补齐桌面借用路径并收紧 SDK 校验，见 [后续完善报告](abi-refine-20261011.md)。
本文保留本轮当时的实现状态和测量数据，避免混淆两次工作。

本轮采用两个 PXA 导入：`pxa.core.v2::pxa_call` 与 `pxa.core.v2::pxa_io`，删除
`pxa_submit` 的 Wasm 兼容入口。控制面收敛用于减少协议重复；游戏收益主要来自扫描线
精简和可选的同步命令借用，不能把帧率提高归因于函数改名或导入数量。

这是允许破坏性更新的探索实现，**只迁移 SDK 测试示例和私有测试包**。正式应用的
源代码、包清单和设备存档没有批量迁移。Core 1 包不能在本轮 Core 2 固件运行；正式
部署需要另外安排应用迁移。本轮设备验证后恢复原应用分区固件。

## 接口边界

| 入口 | 职责 | 输入生命周期与完成方式 |
| --- | --- | --- |
| `pxa_call(route, token, ptr, len)` | 创建、配置、控制、异步服务请求 | 输入仅借用到返回；需延后使用的数据由服务保存；结果通过带 token 的事件完成 |
| `pxa_io(handle, op, ptr, len)` | 已创建资源的读写和批量操作，包括整帧 DrawList | 校验所属组件、类型、代际及内存范围；资源不可用返回 `would-block` |

这里的“两入口”仅指 PXA 自定义 Host 导入，Guest 还可按声明使用 WASI 导入。两者
不是所有工作都经过一个字节包的分发器：Call 的路由和 token 是参数，I/O 直接操作
已获得的资源。内部原生测试保留串行化消息 helper，不构成旧 Wasm ABI 兼容。

- C++ `Transport` 只有一条调用路径，Wasm32 尺寸 16 B，无 scratch、Submit/direct
  编译分支、`PrebuiltPacket` 或预封包 API。相对本轮 Core 1.1 Call 基线，尺寸仍为
  16 B；不能重复计入上轮从 536 B 降到 16 B 的收益。
- 请求编码从载荷偏移零开始，不再预留 20 B 请求信封；事件仍使用规范中的 20 B
  信封。Canvas 固定容量不变，实际编码头 32 → 12 B。IPC 生成器同步修改。
- 协程 owned 请求保留必要的生命周期快照，只复制已初始化的载荷。不能把跨挂起点
  的全部复制删除；borrowed API 要求调用者负责相应寿命。
- Core 主版本只决定导入契约；服务版本独立演进。原生服务的 32/64 位 helper 用
  显式 wire profile 区分，所有 Core 2 Guest 使用 64 位句柄，避免每次 Core 升级都
  意外改变句柄载荷布局。
- 签名工具、WAMR 导入检查和包激活均拒绝旧 Core。服务准入使用 Host capability
  profile 的 ID、版本和 feature，不再维护第二份固定服务 ID 白名单。
- 保留 4076 B 控制输入上限，输入预算与事件池预算分别命名。批量内容走资源 I/O。
  请求槽、资源和线性内存已有显式容量配置；本轮未把固定事件池扩成逐次动态分配，
  也未通过扩大所有应用的默认缓冲来解除上限。

迁移细则：[Core 2 migration](../../spec/draft/abi-2.0-migration.md)，完整语义：
[core-wire.md](../../spec/draft/core-wire.md)。五个测试示例为 i18n、sdk-patterns、
declarative-ui、service-safety、abi-control-bench；旧 ABI 压力/IPC 用例使用私有
staging 副本。其它示例和正式应用保留原版本，不能据此声称全应用矩阵已迁移通过。

## 分发和复制能消除到什么程度

PXA 服务表原本已有哈希索引，句柄已有槽位与代际校验。新增第三个导入仍需进行
Wasm 内存边界、权限、生命周期及资源校验，不等于消除 Host 边界。暂不增加逐材质、
逐图元导入或重复 dispatch 表，以免增加维护面且破坏批处理。

`game-render` 0.6 增加可选 `RenderOptions::borrow_commands`，默认关闭：

1. Guest 用已有 `pxa_io` 提交完整 DrawList。
2. ESP Host 同步校验、绑定资源快照并光栅化，已有辅助 worker 在返回前结束使用。
3. 返回后 Guest 可立即覆写命令；Host 不保留 Guest 指针。Host 自有帧缓冲继续异步
   显示，保留帧缓冲租约、背压、Z-buffer 和透明孔洞处理。
4. 帧缓冲忙时返回 `would-block`，不接受命令、不消耗 frame ID。组件关闭等待已有
   使用结束，隐藏、锁屏或不可见图层不会继续光栅化。

这条路径去掉实际命令 memcpy 和三块 48 KiB mailbox，总计 147456 B；没有新增
默认缓存、线程或分配。校验和光栅化共用原排队模式执行器。桌面后端目前在创建时
明确返回 `unsupported`，不会假装支持然后异步保存借用指针。

没有实现“异步借用可写 Guest 命令”：固定线性内存位置只能防止搬迁，不能阻止返回后
修改命令，可能造成验证与执行读取不同内容。未来可探索 Host 不可变网格资源、明确
所有权转移的共享缓冲，但它们需要计算几何重复存储、句柄/同步开销与峰值内存。
本轮不为这些候选宣称收益。

## 采用和暂缓的方案

| 方案 | 原因 / 结果 | 内存及验证 |
| --- | --- | --- |
| Call/io 收敛、载荷直接编码 | 删除重复协议及 SDK 分支；新增服务无需新增 Core 导入 | 无默认缓存增长；SDK、导入、激活、自定义服务准入回归通过 |
| 纯色/透视路径省去无效仿射 UV，恒定光照省去插值 | 减少不需要的逐像素计算，保留异常倒数端点的仿射回退 | 不新增存储；旧新光栅器所有既有场景颜色、深度、遥测逐字节一致 |
| 同步借用 DrawList | 省去命令复制和 mailbox；真机显示 FPS、输入均值改善 | 命令存储少 144 KiB；资源替换、背压、关闭竞态、输入覆写及隐藏回归通过 |
| 无 Z 多边形排序 | 开放世界、树叶孔洞和相交几何不能可靠处理 | 不采用；无画质降级 |
| 第三个专用热导入 | 当前无独立实测证明其收益超过维护成本 | 暂缓；没有增加导入或查找缓存 |
| SIMD、新 worker、Host 网格缓存 | 当前证据不足，可能增加峰值或复杂度 | 暂缓；下一热点仍是约 25 ms 的 Guest 几何 |

参考 micropixel 最新获取的提交 `4234dbc9db43ed63491254b42fc7d767ff844de4`，检查
`RasterService::Submit` 同步借用、专用扫描线及显示所有权。原仓库存在本地改动，
使用独立 detached worktree，未修改原目录；其纹理上传仍有复制。借鉴的是明确的
消费边界和专用内核，不是照搬无深度的绘制排序。

## 实测和验证结论

pai-touch 实际串口 `/dev/ttyACM1`，固定 S2 场景、296×240、视距 24，三次独立应用
启动。Wasm/AOT 为 O3，Host raster 保持原来的 O2。比较基线为本轮开始时的
**Core 1.1 Call**，并非早期 Submit 或 C 语言游戏：

| 指标 | 基线 | Core 2 排队 | Core 2 借用 |
| --- | ---: | ---: | ---: |
| 实际显示 FPS，三轮平均 | 12.370 | 12.640 | 13.083 |
| Host raster，ms | 36.680 | 35.494 | 33.005 |
| 输入采样 → LCD 完成，ms | 123.118 | 120.382 | 115.943 |
| 稳定 PSRAM 三轮最大值，B | 2967636 | 2963616 | 2811308 |
| 本次启动 PSRAM 真实峰值，B | 3713912 | 3709896 | 3557260 |

借用模式显示 FPS 比基线高 5.76%，比最终排队模式高 3.50%；输入到 LCD 完成的样本
均值低 5.83%。这是这一场景的小样本结果，没有证明其它游戏或设备都加速。提交耗时
反而 38.984 → 40.432 ms，因为同步调用包含渲染工作；只看提交 FPS 会误判。

最终控制取消微基准每轮 32×1000 次：冷启动批中位数为 10.488 / 10.497 / 10.464 µs，
恢复为 10.434 / 10.575 / 10.439 µs；与上轮 Call 的约 10.5 µs 持平。这是完整边界、
门禁与取消操作的合计，**没有独立分离 FFI、查找、校验或 memcpy 各自耗时**。

SRAM 稳定最大值均 273088 B；基线/借用整次启动峰值均 277276 B。最终排队组启动
峰值多 76 B，借用组稳定窗口峰值多 12 B，来源未独立定位，不能宣称每个窗口严格
不增长。静态 SRAM/PSRAM、Guest 线性内存及代码映射相同；总 PSRAM 明确降低。
未测 FreeRTOS 各任务栈最高水位，不将堆峰值冒充任务栈使用量。

完整游戏证据、分阶段、内存及复现命令在 pxa-apps 仓库：
`voxel-craft-cpp/docs/performance/abi-core2-20261011.zh-CN.md`。
本报告配套 [证据索引](abi-next-20261011/validation.json) 和
[控制微基准](abi-next-20261011/control-final.json)。

- C++ SDK 完整脚本通过：56 个单元、配置/诊断/国际化/IPC 等附加检查。
- Host 32/32；ESP backend ASan+UBSan 及借用模式回归通过。
- 模拟器 88 项覆盖：首轮 82 项通过；迁移测试 fixture、修复测试编码及延长 O3
  编译超时后，剩余六项分别复跑通过，光栅与最终准入另外通过。不是一次 88/88 的日志。
- C SDK 17 个独立单元通过。依赖未迁移正式 C 游戏的完整应用矩阵不纳入本轮通过
  声明；旧 `pxa_submit` 调用按预期无法编译。
- 真机固定场景、转向输入、三次启动均通过；最终排队模式前后台三次切换通过。
  借用模式隐藏/锁屏/并发关闭在原生后端回归中验证，未做真机全游戏玩法矩阵。

没有把旧 C 游戏和本轮 C++ 的不同工作负载当成语言性能对比，也没有把一次重构当成
端到端“零开销 ABI”。当前可采用的边界和可选优化已有代码、回归和实测；后续正式
迁移、桌面借用后端、任务栈水位和更广场景尾延迟仍需单独验证。
