# Core 2 后续完善与验证（2026-10-11）

本轮基于 [Core 2 探索结果](abi-next-20261011.md) 继续完善，保留 `pxa_call` / `pxa_io`
两入口。主要收益是桌面后端与 ESP 的语义一致、减少桌面命令存储，以及更严格的 SDK
协议检查。本轮没有新增导入，也没有改动 ESP 生产代码的光栅热路径。

## 采用的改动

| 改动 | 原因和收益 | 存储与验证 |
| --- | --- | --- |
| 桌面支持 `RenderOptions::borrow_commands` | 同一个游戏可在桌面和设备验证同步命令借用，不再在桌面创建时失败 | 返回前执行，返回后只保留 Host 像素；不分配命令副本 |
| 桌面排队模式只保留一个待执行命令缓冲 | 提交和光栅化都在产品线程串行执行，两个命令缓冲没有并行价值 | 48 KiB 配置下 98304 → 49152 B；资源快照仍保留 |
| 两种模式共用目标构造、光栅执行和遥测累加 | 减少重复分支，便于后续修正材质、深度和统计 | `product_host_t` 在本机 64 位构建中 31840 → 31392 B，减少 448 B |
| 隐藏/后台拒绝借用提交，待显示时施加背压 | 避免不可见光栅化和覆盖等待显示的帧 | 沿用已有 framebuffer pending 状态；`would-block` 不消耗 frame ID |
| C++ 创建结果验证 | 防止零容量、错误尺寸、非法缩放/能力掩码或畸形结果进入 Renderer | 仅创建阶段检查，无新增对象字段或逐帧分配；异常返回的句柄由 RAII 关闭 |
| 规格、Host、C++ 容量/能力一致性检查 | JSON 曾只有 5 个 capability、16 个纹理槽和 768 条命令，与实现不符 | 对齐为 16 个 capability、48 个纹理槽、1024 条命令；构建检查防止再次漂移 |
| 修正 ESP 原生测试的分配大小断言 | 普通 malloc 可把 32 B 深度平面向上取整，ASan 的 usable size 不同 | 检查实际分配量；不改生产分配策略 |

默认仍是排队模式。借用模式把光栅 CPU 工作放进提交调用，适用于愿意承担这段同步
CPU 时间的游戏；它不会等待 LCD，但可能因没有可用帧缓冲返回 `would-block`。
应用应在后续帧回调重试或构建最新场景，不要忙等。

桌面单命令缓冲依赖产品线程串行执行这个明确前提。未来若增加光栅 worker，必须
重新设计执行中命令的所有权，不能直接从另一个线程读取这一待提交缓冲。ESP 有
并行显示/执行关系，不能照搬桌面的单缓冲删减。

## 正确性和边界

- 借用返回后立即覆写 Guest 字节，不改变已生成画面；同一帧只显示一次。
- 背景、隐藏、背压、关闭待显示帧、关闭后重建均有桌面后端回归。
- 无效替换提交不覆盖已接受的命令/资源，也不消耗下一有效 frame ID；此共享场景
  同时在真实桌面后端和原生 ESP 后端运行。
- 排队帧继续引用提交时的纹理/调色板；替换、撤销和关闭正确释放引用。
- C++ 测试覆盖 17 个畸形创建结果及精确一次关闭；缩放移位前先检查范围，宽高乘法
  提升为 32 位，避免畸形值触发非法移位或截断。
- SDK 使用 `pxa::game::limits` 的命名常量；没有添加模板缓存、大型临时容器或默认
  资源。现有 C++26 API 和线性内存需求保持一致。

## 实测范围

详细数值、原始 JSON、图像及复现入口放在 pxa-apps 仓库：
`voxel-craft-cpp/docs/performance/abi-core2-refine-20261011.zh-CN.md`。

真实 voxel AOT 在 296×240 / 160 DPI 和 454×454 / 305 DPI 圆屏配置中，各执行到
160 个可见帧，并覆盖前后台恢复。旧桌面排队、新排队、新借用输出逐字节一致；
每组 160 rendered / 160 visible / 0 dropped。截图为圆屏裁切前的游戏 Surface，
不能当作最终圆屏安全区或 HUD 布局的完整验证。

pai-touch 使用 `/dev/ttyACM1`，同场景旧 SDK 包复测 **13.143 FPS**，新 SDK 包
**13.204 FPS**；Host raster **32.899 → 33.034 ms**。这些差异不支持宣称本轮
提升了 ESP 帧率；显示和渲染基本持平。本轮输入采样到 LCD 完成均值 **114.122 ms**，
上一轮为 115.943 ms，未证明尾延迟改善。

桌面微基准两轮结果受宿主调度/频率波动影响，变化方向不一致，保留全部数据，不作
CPU 百分比收益结论。确定的收益是排队命令存储减半、借用命令存储为零，以及共用
执行代码。仍然需要保留协议校验、资源所有权、Z-buffer 和透明孔洞处理。

设备 WAMR、Guest 线性内存、代码映射、帧缓冲、深度缓冲、命令存储均相同。全机
PSRAM 稳定窗口峰值有一次比旧包三轮最大值高 572 B，另外两次更低；启动峰值和
稳定占用更低。这不能证明每次全机峰值严格不增，完整原始数值在应用报告中列出。
本轮没有增加 ESP 运行时分配或默认存储。

## 验证结果和交付边界

- C++ SDK 完整 Host 测试脚本通过。
- 桌面/Host CTest 84/84 通过；4 个较重的 SDK fixture 不计入该数字。
- `service-safety` 真实 AOT 在 3 种模拟器配置另行通过。
- 桌面后端的 ASan/UBSan 回归通过；该测试的后端编译单元有插桩，链接的既有库未
  全部重新插桩，不能称为整个模拟器都经过 sanitizer。
- ESP adapter Host 测试普通构建及 ASan/UBSan 构建通过。
- 规格正向检查通过；内存中故意改错能力位/命令上限的负向检查均正确拒绝。
- 真机新旧包各 3 次启动/停止、固定场景采集，新包另有 3 轮输入转向检查；画面无
  场景差异。没有在本轮重做完整背包、编辑重建及所有正式应用矩阵。

仅私有测试副本迁移，正式游戏源码和清单保持原版本；旧版本兼容性限制仍见前一份
报告。设备只写应用固件分区，结束后已恢复原固件，删除私有测试包，保留原有 5 个
应用及数据；Counter 启动/截图/停止验证通过。没有修改持久设置，没有提交 Git。
