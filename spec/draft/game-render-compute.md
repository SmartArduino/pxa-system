# GameRender compute protocol 1.5

`CREATE_RASTER_CONTEXT` (3) takes `max_commands:u32, reserved:u32=0`.
The limit is 1–4096. Its successful reply is `status:i32=0, handle:u64,
max_commands:u32, reserved:u32=0`. A compute context owns only bounded counters;
it allocates no display, image, projection workspace or depth buffer.

| Operation | I/O | Capability bit | Purpose |
| --- | --- | --- | --- |
| BLIT_INDEXED_FRAME | 0x108 | 4 | INDEX8/palette/cursor resolve on the established 320×240 sampling grid |
| BLIT_INDEXED_RECT | 0x109 | 5 | Exact nearest-neighbour rectangle resolve |
| EXECUTE_PRIORITY_TILES | 0x10a | 6 | Ordered INDEX8 tiles with RGB565 and priority outputs |
| COMPUTE_TELEMETRY | 0x10c | — | Synchronous compute counters |

The machine-readable layouts are in `pxa-game-render.json`. Host, C and C++
codecs are generated by `tools/generate_game_render_compute.py`. There are no
engine projection or hardware-specific lighting structures in this protocol.
Applications perform projection, depth updates and source-format conversion.

## Borrowed frame resolve and priority tiles

The indexed frame/rectangle operations borrow INDEX8 pixels, a palette and an
optional cursor from Guest memory, producing RGB565 output. Sources and packet
bytes must remain immutable through the synchronous call. Strides and source
ranges are checked before output writes. Exact rectangle sampling is separate
from the established 320×240 sampling grid.

Priority tile batches contain ordered INDEX8 tiles, palettes and per-pixel
priority values. Validation completes before writes to either output plane.
Worker ranges own matching priority bytes and RGB565 pixels; all workers finish
before returning. Contexts retain no Guest pointers or rendering workspace.
The schemas in `pxa-game-render.json` define the layouts and bounds.

C uses `pxa_game_render_compute.h` and `pxa_game_render_tiles.h`; C++ uses
`RasterContext` and `PriorityTileBatch`. Projection, lighting and texture
sampling stay in applications. Short positive I/O replies are protocol errors.

## Telemetry

`COMPUTE_TELEMETRY` writes exactly 64 bytes: six u64 values (`batches`,
`rejected`, `commands`, `pixels`, `validation_us`, `execute_us`), followed by
four u32 values (`last_validation_us`, `last_execute_us`, `max_commands`, zero).
Telemetry does not retain Guest pointers or allocate a workspace.
