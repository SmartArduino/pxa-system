# C++26 SDK implementation notes

Paths below are relative to the installed DevKit. SDK source and app templates are included; `sdk/guest-cpp/README.zh-CN.md` documents supported features. C++26 does not imply that every experimental language or standard-library feature is supported by the pinned Clang/libc++ or WASI environment.

- Start from `sdk/templates/hello/main.cpp` and its CMake config. The SDK config sets the checked compiler requirements, O3, ABI definitions and no-exception/no-RTTI options. Do not replace these with a host compiler or a different Wasm toolchain.
- Declarative UI: `pxa/app.hpp`, `ui_component.hpp`, `ui_environment.hpp`, `ui_layout.hpp`, `ui_modifiers.hpp`. `Environment` initializes from app configuration and handles display events; `SafeArea`, dp units and semantic fonts handle DPI and screen geometry. Check layout on both round/high-DPI screens and small rounded screens. Only touch targets that are actually visible count as usable.
- Immersive backgrounds: `SafeArea(...).background(Color::background)` paints its full-size container, including padding, as in the hello template. A full-size parent background with a SafeArea content child also works for scenery or decorative images. Keep text, HUD and input targets within the safe region and use a continuous page background unless a distinct card is intentional. For Surface games, draw scenery over the full Surface and keep the HUD overlay transparent; an opaque SafeArea background would cover the game. Retaining a readable status bar can still look immersive; hide bars when appropriate for the requested experience.
- Insets: newer Hosts report physical `DisplayMetrics.safe`, visual `system_bars` and active input `system_gestures` separately in START and updates. `SafeArea` combines shape, physical and bar margins with max and protects bottom Home input by default; it does not shift a whole page for a side Back gesture. Check edge controls/drag areas for conflicts and use `SafeArea(metrics, controls, GestureAvoidance::all)` on that group when needed. Do not assume all devices have gestures. Hidden status bars reserve no top height; hidden buttons release their space; active invisible gestures remain input regions. The corresponding `*_known=false` means unknown on an older Host. Window 0.4 still reports combined legacy bar/input insets, so do not copy its side input exclusion into page padding. Re-layout on actual metrics rather than hardcoding heights.
- Layout: Row/Column shrink to content unless `.fill()` is requested. Use `.visible(State<bool>)` for adding/removing detail in one responsive page. `When` suits distinct subtrees; height-filling branches need an explicitly bounded conditional container. Button modifiers can precede actions (`Button("Start").height(44_dp).on_click(...)`); bind an action before placing the completed view. Inspect UI errors and actual screenshots, including all requested screen shapes.
- Input/text: `text_input.hpp`, `ui_action.hpp`, `ui_controller.hpp`; request system input instead of implementing another default keyboard. Internationalization: `i18n.hpp`, `i18n_ui.hpp`, `locale.hpp`; use stable message IDs and runtime language changes rather than duplicated view trees.
- Games: inspect `game_service.hpp`, `surface.hpp` and the relevant existing game before choosing a drawing path. Use elapsed monotonic time for simulation; batch drawing, reuse scratch storage and keep allocations out of a per-frame loop. Transparent cutouts need depth semantics. Submission FPS is not display FPS.
- Audio/resources: `audio.hpp`, `assets.hpp`; schedule voices/tracks and preload only the resources needed now. Verify onset timing on hardware when latency is a requirement. Storage/network/work: `storage.hpp`, `fs.hpp`, `net.hpp`, `work.hpp`; use typed handles and scoped ownership, and handle cancellation and permission denial.
- `package.json` declares services, WASI features, permissions, assets and memory limits. Do not fix a missing capability by raising every service to the newest version or inflating all budgets. Inspect the precise build/runtime error first.

For actual firmware/Host changes, read the source integration documentation and the board's build instructions; these notes are about Guest applications.

- Screen direction (Window 0.5): use `ctx.window().request_orientation(pxa::OrientationPreference::landscape)` or `portrait` for a layout preference, including from an in-game settings button. Use `set_rotation(pxa::DisplayRotation::deg90)` only for an exact reading direction. `snapshot(true)` obtains rotation (quarter turns), native dimensions and `supported_rotations`; consume `on_window_changed` and Environment updates to rebuild/reflow from actual dimensions. Native orientation can be wide or tall; portrait is height > width, landscape is width > height. Equal dimensions are square: shape preferences retain the angle; explicit 0/90/180/270 still work. Do not force a square device to rotate just to satisfy a landscape request. Unsupported boards can expose native only; show a useful fallback. Home/exit restores system direction. Sensors keep native Android axes (+X right, +Y top, +Z out); map tilt vectors with `pxa_display_motion_to_screen` and the current rotation once, only when game controls follow the screen. See `sdk/guest-cpp/examples/orientation` for a runnable example.
